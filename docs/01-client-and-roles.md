# Клієнтська частина та ролі користувачів

Документ закриває вимоги лабораторних робіт № 3 (опис клієнтської частини, ролі клієнтів, адміністрування) і № 4 (форми для різних категорій користувачів, завдання кожної категорії).

## 1. Архітектура клієнтської частини

| Шар | Технологія | Призначення |
|---|---|---|
| Клієнт (SPA/SSR) | Next.js 16, React 19, TypeScript, Tailwind CSS, shadcn/ui | Екранні форми, таблиці, модальні вікна, сповіщення (react-hot-toast) |
| Сервер API | ASP.NET Core (.NET 10), REST, JWT | Бізнес-логіка, перевірка прав, валідація (FluentValidation) |
| Сховище | MS SQL Server, Entity Framework Core | Дані автопарку, маршрутів, журналу дій, облікових записів (ASP.NET Identity) |

Клієнт отримує JWT-токен під час входу і зберігає його в cookie `token` (термін дії — 24 години). Сторінки рендеряться на сервері Next.js: перед завантаженням даних перевіряється наявність токена, а для адміністративних сторінок — ще й роль `Admin`. Без токена користувача переадресовує на `/login`, а користувача без ролі `Admin` з адміністративної сторінки — на головну.

## 2. Категорії користувачів

| Роль | Хто це | Як з'являється в системі |
|---|---|---|
| **Адміністратор** (`Admin`) | Керівник автопарку | Створюється автоматично під час першого запуску (`IdentitySeeder`) |
| **Диспетчер** (`Dispatcher`) | Працівник, що планує й супроводжує рейси | Реєструє адміністратор на сторінці «Диспетчери» |

Гостьового режиму немає: усі екрани, крім входу, потребують авторизації.

## 3. Завдання кожної категорії користувачів

### Адміністратор
1. Вести довідник **водіїв**: додавати, редагувати й видаляти їх (водія, призначеного на рейси, видалити не можна).
2. Вести облік **автомобілів**: додавати, редагувати, видаляти авто й змінювати їхній статус.
3. Реєструвати **техобслуговування** авто й позначати його завершеним.
4. Вести довідник **локацій** (міст і країн): додавати й видаляти (локацію, що використовується в маршрутах, видалити не можна).
5. Керувати **диспетчерами**: реєструвати й видаляти облікові записи.
6. Переглядати **журнал дій** (хто, коли і що змінив).
7. Виконувати всі завдання диспетчера.

### Диспетчер
1. Створювати **маршрути**: обирати пункти відправлення й прибуття, час, водія й автомобіль.
2. Редагувати активні маршрути: змінювати локації, водія, авто й статус.
3. Змінювати статус рейсу: «Розпочати», «Завершити», «Скасувати».
4. Видаляти маршрути.
5. Шукати маршрути за містом, датою відправлення, статусом, водієм чи автомобілем.
6. Формувати **звіти за період** (день, тиждень, місяць).
7. Змінювати статус автомобіля (наприклад, у разі поломки в дорозі).

## 4. Матриця доступу до API

| Ресурс | Перегляд | Створення | Редагування | Видалення |
|---|---|---|---|---|
| Маршрути (`/api/Route`) | усі автентифіковані | Admin, Dispatcher | Admin, Dispatcher | Admin, Dispatcher |
| Пошук і звіт маршрутів (`/api/Route/search`, `/api/Route/periodReport`) | Admin, Dispatcher | — | — | — |
| Автомобілі (`/api/Auto`) | усі автентифіковані | Admin | Admin; статус — Admin, Dispatcher | Admin |
| Водії (`/api/Driver`) | усі автентифіковані | Admin | Admin | Admin |
| Локації (`/api/Location`) | усі автентифіковані | Admin, Dispatcher (під час вибору міста у формі маршруту) | — | Admin |
| Техобслуговування (`/api/AutoMaintenance`) | усі автентифіковані | Admin | Admin | Admin |
| Облікові записи (`/api/Account`) | Admin | Admin (реєстрація) | — | Admin |
| Журнал дій (`/api/AuditLog`) | Admin | автоматично | — | — |

Без токена всі ендпоінти, крім `POST /api/Account/login`, повертають 401.

Верхнє меню (`components/header.tsx`) показує кожній ролі лише її пункти:

| Пункт меню | Шлях | Admin | Dispatcher |
|---|---|:-:|:-:|
| Головна | `/` | ✓ | ✓ |
| Водії | `/driver` | ✓ | |
| Авто | `/auto` | ✓ | |
| Диспетчери | `/dispatcher` | ✓ | |
| Маршрути | `/route` | ✓ | ✓ |
| Звіти | `/report` | ✓ | ✓ |
| Журнал дій | `/audit-log` | ✓ | |

### Перелік екранних форм

| Екран | Тип | Вміст |
|---|---|---|
| Вхід (`/login`) | форма входу | Логін (або email) і пароль |
| Головна (`/`) | панель | KPI-картки (авто, водії, активні рейси), останні 5 маршрутів, панель швидкого переходу |
| Водії | таблиця + модальні вікна | Пошук за ПІБ і посвідченням; форми «Додати водія» й «Редагувати водія»; видалення |
| Авто | таблиця + модальні вікна | Пошук; форми додавання й редагування; зміна статусу; вікно техобслуговування (історія ТО, нове ТО, завершення ТО) |
| Диспетчери | таблиця + модальне вікно | Пошук; форма реєстрації диспетчера; видалення |
| Маршрути | картки + форми | Форма розширеного пошуку (місто відправлення, місто прибуття, період відправлення, статус, водій, авто); швидкий пошук за містом; форми «Додати маршрут» і «Редагувати маршрут» з пошуком міст через геокодування; кнопки зміни статусу; карта маршруту (Google Maps) |
| Звіти | форма + звіт | Вибір періоду (готові варіанти «Сьогодні», «Останні 7 днів», «Поточний місяць» або довільні дати); показники за статусами; години в дорозі; навантаження водіїв; перелік рейсів; друк |
| Журнал дій | таблиця | Фільтр за типом дії; пошук за користувачем і ID об'єкта |

## 6. Можливості адміністрування

- **Внесення змін у БД**: довідники водіїв, авто й диспетчерів змінюються через форми, а локації створюються автоматично, коли диспетчер вибирає місто у формі маршруту; перед збереженням дані перевіряються і на клієнті, і на сервері.
- **Доповнення**: нові записи додаються через модальні вікна «Додати …».
- **Пошук**: кожна таблиця має рядок пошуку; маршрути шукаються на сервері за кількома критеріями одночасно.
- **Контроль цілісності**: сервер не дає видалити водія, авто чи локацію, які використовуються в маршрутах, і не дає видалити власний обліковий запис.
- **Аудит**: кожна зміна (створення, редагування, видалення) записується в журнал дій з користувачем і часом. Якщо обліковий запис видалили, історія його дій зберігається.
